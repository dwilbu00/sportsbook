## approach_name
Gate-first minimal GameContext with a starter-neutralized team-run→hits reconciliation scalar riding the prop_features seam

## one_line_thesis
Build one cached, leakage-safe, analytic GameContext per game from the xwOBA expected-runs path, and expose exactly ONE per-batter MEAN multiplier — a starter-neutralized team-run→hits reconciliation index — that rides the existing prop_features registry + confirmation gate identically to `rest`, deferring every variance/correlation piece the single-prop Brier gate cannot see.

## scope_summary
BUILT: (1) a shared analytic GameContext (mlb_starters.build_game_context / gamecontext_factor) unifying the three run estimates — per-team run means from expected_runs_from_factors, a joint run/total PMF via the refactored poisson/negbin `probabilities()` inner (the discarded joint now retained), and a runs→hits mean mapping; (2) ONE gate-validatable per-batter scalar `gamecontext_strength` registered in prop_features, plumbed into the offline obs via a new _attach_gamecontext step in join_book_lines_to_actuals, so --feature-diag yields the first gate verdict with ZERO refit/grid/write changes; (3) runtime + sweep parity wiring (phase 3, only if the verdict clears). NOT built: variance/tail-shape method (mean-preserving → gate-invisible), batter-to-batter correlation for parlays, the full runtime bottom-up reconciliation r against the real lineup sum, any use of leaky season-to-date splits, and any Monte-Carlo. Whitelisted to batter_hits.

## gamecontext_object
mlb_starters.build_game_context(home_team, away_team, date, season, team_index=None) -> dict, memoized in a module-level _GC_CACHE keyed (home_abbr, away_abbr, date) with the game_results._SCORE_CACHE pattern (completeness flag + TTL; get_expected_runs_team_factors is itself 24h-cached). Fields: {complete: bool, mu_runs: {home, away}, run_pmf: {home:[..30], away:[..30]}, total_pmf:[..60], total_mean, total_std, team_hits_mean:{home,away}, gc_factor:{home,away}}. Run means come ONLY from the leakage-safe xwOBA path: get_expected_runs_team_factors(season, as_of=date) (cutoff=date-1d) fed to expected_runs_from_factors — NEVER get_team_offense_splits/get_team_bullpen_quality (season-to-date, leak). run_pmf reuses the existing `probabilities(expected)` inner of poisson_margin_probability (refactored to a public _run_pmf(mu, dispersion, max_runs=30) so the joint is no longer discarded); total_pmf is the discrete convolution of the two (this is the unify point for totals-estimate #1 and the currently spread-only joint-estimate #2). team_hits_mean[side] = H_LG * (mu_runs[side]/R_LG)**EPS (EPS≈0.55, hits less volatile than runs; constants module-level, fit-elsewhere note like the existing LEAGUE_AVG). Leakage handling: if expected_inputs is None or either abbr unmatched, complete=False and gc_factor defaults to 1.0 (fail-open no-op, preserving strength-0 byte parity). TTL/completeness guard mirrors _SCORE_CACHE so a stale probable/lineup cannot pin a mispriced game; note gc_factor deliberately needs NO probable-starter fetch (see math), only the two team abbrs + date, so it is fully computable over historical backtest dates where get_probable_starters would fail.

## math
Pipeline (per side; gate uses the batter's own side): (1) run means — own_off = mean over hands H∈{L,R} of clamp(offense_vs_hand[H][own_abbr]/league_xwoba, 0.5..2.0) [hand-averaged so no probable-starter hand is needed offline]; opp_bull_supp = clamp(league_bullpen_xwoba / bullpen_xwoba[opp_abbr], 0.5..2.0) (>1 = better bullpen → fewer hits). (2) team-run dist — mu_runs[side]=expected_runs_from_factors(R_LG, own_off_full, opp_staff_full) for the OBJECT (full starter+bullpen, for totals/spread), via _run_pmf → convolution → total dist. (3) team-hits mapping — team_hits_mean = H_LG*(mu_runs/R_LG)**EPS. (4) per-batter allocation — the gate scalar is the reconciliation factor computed against a LEAGUE-AVERAGE lineup baseline (the only baseline available per-obs, since the offline obs has no lineup): the batter's independent projection already prices his own skill + (via matchup_mult) the opposing STARTER, so gc_factor neutralizes the starter and keeps only the residual the projection cannot see: eff_supp = STARTER_SHARE*1.0 + BULLPEN_SHARE*opp_bull_supp (STARTER_SHARE≈0.62 constant, starter pinned to neutral 1.0 = owned by matchup_mult); run_index = own_off / eff_supp; gc_factor = clamp(run_index**EPS, 1-RUN_CAP .. 1+RUN_CAP) with RUN_CAP≈0.10. (5) reconciliation/feat_mult — the prop_features fn returns feat_mult = clamp(1 + strength*(gc_factor-1), 1-CAP .. 1+CAP), CAP≈0.08, exactly REST's shape. Runtime-only refinement (deferred, in the object not the gate): true r[side]=team_hits_mean[side]/Σ_i h_i over the confirmed lineup (get_confirmed_lineup + lineup_player_context exposure). Reused stdlib primitives: expected_runs_from_factors, the poisson/negbin `probabilities()` inner (→_run_pmf), stats._weighted_mean, math only; NO MC. Byte-parity: strength 0 → strengths_from_params drops it → projection_multiplier returns 1.0 → projected AND line unchanged.

## gate_story
Per-batter scalar: feat_mult = clamp(1 + gamecontext_strength*(gc_factor-1), 1-CAP..1+CAP), a MEAN shift on the batter's expected hits — gate-visible because project_and_empirical does projected*=feat_mult and line_eff=line/feat_mult (moves methods A/B/C/E alike), identical to how `rest` and combined_mult behave. Plumbing (the CRITICAL gap solved): a new _attach_gamecontext(enriched, season) called at the END of join_book_lines_to_actuals groups the enriched per-player obs by (home_team, away_team, game_date), builds the GameContext ONCE per game, and writes obs["gc_factor"] = context["gc_factor"][ own-side ] where own-side = home if test_game.is_home else away (home_team/away_team already ride each obs via **row; is_home via test_game). project_and_empirical then passes it through: projection_multiplier gains one optional kwarg gamecontext_factor=obs.get("gc_factor") which it merges into ctx; the new registry fn reads ctx["gc_factor"]. NO new arg to build_real_line_obs (obs already flows through it). Because diagnose_features iterates FEATURE_REGISTRY and injects params['features']={name:strength}, adding the registry entry makes --feature-diag score gamecontext through the EXACT ship-path gate (select_method_at_real_lines, 2-fold _variant_confirms/_confirms) with NO change to diagnose_features/refit — that is the first verdict, offline + free + no-write. Validated INSIDE the gate: the Brier mean-at-line improvement + the 2-fold confirmation; diagnose_features already prints consensus-priced ROI ALONGSIDE Brier as a co-signal (Brier decides). Validated OUTSIDE the gate: nothing for the shipped mean shift (unlike matchup_mult, which sidesteps the gate and is checked in backtest_props) — this is deliberately gate-native. The DEFERRED pieces (full lineup reconciliation r, batter-batter correlation) would be validated outside via backtest_props / parlay CLV when built, since single-prop Brier is blind to them.

## parity_plan
Three-way parity via ONE shared source, exactly like prop_features is for rest: mlb_starters.gamecontext_factor(own_team, opp_team, date, season) is the single implementation; all three paths resolve to the same (own, opp, date, season) and feed the identical scalar into prop_features.projection_multiplier(...gamecontext_factor=gc). (a) offline real-line: gc attached in join_book_lines_to_actuals, read in project_and_empirical (:598-606 block). (b) synthetic sweep: backtest.run_player_props_backtest already carries player_team_name, upcoming_opp, upcoming_is_home, upcoming_date, season_year at :2662 — compute gc inline there and pass it in the same projection_multiplier call (mirrors the rest block at 2662-2671 and the line-shift at 2706). (c) runtime: props.analyze_player_props_value has home_team_name/away_team_name/upcoming_is_home/commence_iso/season — compute gc inline in the rest block (props.py:1245-1249) and fold into combined_mult/effective_line (:1251/:1258). Parity self-check: strength 0 → 1.0 everywhere → byte-identical to production (the invariant --feature-diag asserts). NOTE the ONLY intentional bypass: the joint total_pmf / reconciliation r in the GameContext object is NOT run through the props gate (single-prop Brier can't see a total distribution) — it is matchup_mult-style, reserved for the totals market path and the deferred parlay-correlation consumer, and will be validated on its own axis.

## double_counting_mitigation
gc_factor is engineered to be maximally orthogonal to every adjustment already in combined_mult, so it REPLACES rather than stacks: (1) opposing STARTER is pinned to neutral 1.0 in eff_supp — it is owned by matchup_mult (the SHIPPED opp0.5 batter_hits log5 starter term); (2) park and weather never enter expected_runs_from_factors at all — owned by park_mult/weather_mult; (3) batting-order exposure is an AB-count effect owned by lineup_mult, whereas gc_factor is a per-AB RATE effect. The only residual overlap is own-team offense vs the batter's own recency projection (his xwOBA is ~1/9 of the team factor) — mild, and the confirmation gate adjudicates it: if the fuller own-offense+opp-bullpen index over-shifts the mean, Brier will not clear MIN_CALIB_BRIER_GAIN in both folds and it ships nowhere (same fate as rest/NegBin-E/xBA/CSW). Conservative fallback if the gate rejects it: drop own_off (set gc_factor=clamp((1/eff_supp)**EPS)) leaving a pure opposing-bullpen residual that is unambiguously double-count-free — a one-line change to the same helper, no new feature. The gate scalar is explicitly the reconciliation r under a league-average-lineup baseline; the real-lineup r (which could re-introduce overlap) is deferred to runtime and kept out of the gate.

## phasing
Phase 1 (inert, independently testable): mlb_starters._run_pmf refactor (extract from poisson_margin_probability, keep its behavior byte-identical) + build_game_context + gamecontext_factor + _GC_CACHE + unit tests (leakage cutoff, fail-open completeness, cap bounds, cache key). Nothing calls it yet → zero runtime change. Phase 2 (delivers the FIRST GATE VERDICT, no-write, free): add the `gamecontext` entry to FEATURE_REGISTRY (props={batter_hits}, strengths (0.0,0.25,0.5), runtime_knob "gamecontext_strength", fn reads ctx["gc_factor"]); add gamecontext_factor kwarg to projection_multiplier; add _attach_gamecontext to join_book_lines_to_actuals; pass obs.get("gc_factor") in project_and_empirical. Run `refit_calibration.py --feature-diag --feature gamecontext --sport mlb` → Brier + ROI co-signal verdict through the real gate. Phase 3 (ONLY if Phase 2 clears): runtime props.py wiring + sweep inline gc in backtest.py (parity) + _parse_variant_name 7-part /gc token + _build_prop_cfg gamecontext_strength + grid axis, so a bare `refit_calibration.py --sport mlb` auto-adopts through the sweep gate. Phase 4 (explicitly out of scope): total_pmf → totals market unification, runtime real-lineup reconciliation r, batter-batter correlation for the parlay consumer, and any new p_dist variance method.

## why_it_wins
It is the smallest design that satisfies the whole mandate and cannot regress: the ONLY behavioral change until the gate speaks rides the same prop_features scalar seam that rest already proved, so strength-0 is byte-identical and the first verdict is a free no-write --feature-diag run with zero changes to the gate, sweep, or refit. It solves the stated plumbing gap minimally (one _attach_gamecontext step + one optional kwarg) instead of reworking the harnesses to be game-oriented. It is leakage-safe by construction (xwOBA expected-runs path only, as_of-1d), and its double-counting story is principled — it neutralizes exactly the terms other multipliers already own (starter/park/weather) and frames the scalar as the reconciliation residual against a league-average lineup, the only baseline computable per single-prop obs. It still BUILDS the full unifying GameContext object (joint run + total distribution now retained instead of discarded), so the deferred totals-unification, real-lineup reconciliation, and parlay-correlation work all have their foundation without paying for the parts the single-prop Brier gate is blind to today.

## top_risks
- Signal too weak to clear the gate: starter-neutralized + own-offense-redundant leaves mostly the opposing-bullpen residual (~38% of PAs), so the mean shift may not beat MIN_CALIB_BRIER_GAIN in both folds — likely ships nowhere on current data (acceptable; same as rest, and the object is still reusable).
- Historical Savant xwOBA coverage: get_expected_runs_team_factors depends on Savant team splits per as-of date; sparse early-season/older dates → complete=False → gc_factor 1.0 for those obs, shrinking the effective sample the gate sees (fail-open, but reduces power).
- Team-name→abbr resolution: obs home_team/away_team are odds-API names; _match_team_id must map them to the StatsAPI abbr namespace get_expected_runs_team_factors uses, or the game silently no-ops (mitigate with the existing _canonical_team_key path + a coverage warn).
- EPS/STARTER_SHARE/RUN_CAP are hand-set constants, not fit — if wrong they bias the mean shift; keep them conservative (small CAP) and note they are fit-elsewhere like LEAGUE_AVG, so the gate still protects against a bad choice.
- Own-offense residual double-counts the batter's own projection subtly; if the gate is fooled by in-sample structure the 2-fold _variant_confirms is the backstop, but watch for a single-split winner's-curse (exactly what the variant gate exists to catch).
