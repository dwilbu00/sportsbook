# SUBSYSTEM
Batter-prop projection path in props.py (analyze_player_props_value + the multiplier stack), plus its per-game feature producer (mlb_starters.build_matchup_features) and Streamlit driver (app.py).

## FUNCTIONS
- **analyze_player_props_value** (props.py:862-1717)
  The whole prop projection+calibration+value gate. Signature: analyze_player_props_value(prop_data, player_histories, threshold_pct=5.0, sport_key=None, team_defense=None, espn_teams=None, safe_mode=False, safe_target=0.95, team_schedules=None, matchup_features=None, weather=None). Two nested loops: for prop_key,players in prop_data['props'] (953) then for player_name,odds_info in players (968). Builds base_proj, combined_mult, avg_stat, effective_line, over_rate per (prop,player) and appends ONE flat candidate dict per player. No team grouping.
- **base_proj assembly (weighted mean + shrink + xBA blend)** (props.py:1122-1171)
  base_proj = _weighted_mean(values, weights) (1122). Bayesian shrinkage toward unweighted season mean if shrinkage_k>0 (1123-1127; MLB default 0). §2.4a xBA blend: base_proj,_ = _xstats_blend(base_proj, xba, ab_per_game, xstats_strength) (1159) — modifies base_proj BEFORE the multiplier stack. These modify base_proj directly; they are NOT factors of combined_mult.
- **combined_mult / avg_stat / effective_line** (props.py:1251-1259)
  combined_mult = output_def_mult * matchup_mult * lineup_mult * park_mult * weather_mult * rest_mult (1251-1252). avg_stat = base_proj * combined_mult (1254). effective_line = line / combined_mult if combined_mult else line (1258). empirical_over = _weighted_rate(values, weights, lambda v: v > effective_line) (1259). This is THE central seam.
- **_output_defense_multiplier** (props.py:62-77)
  output_def_mult factor: 1 + strength*(opp_pa/league_avg -1), clamped [0.5,1.5]. TONIGHT's opponent defense. Applied at 1112-1118. For MLB the default output_def_strength is 0.0 (DEFAULT_PLAYER_PROP_OUTPUT_DEFENSE_STRENGTH=0.0, props.py:243) so this is 1.0 for batters unless calibrated — effectively an NBA feature.
- **_mlb_prop_matchup_mult** (props.py:93-162)
  matchup_mult factor. Signature (prop_key, upcoming_is_home, matchup_features, weight, player_context=None). For batter_hits: reads OPPOSING side's starter quality and log5-blends it into a per-AB rate. Called at 1200-1203 with weight=_starter_adjustment(sport_key,'props',prop_key). Clamped [0.7,1.4] (162).
- **_mlb_lineup_exposure_mult / _lineup_exposure_mult** (props.py:183-207 / 165-180)
  lineup_mult factor (batter_hits only): blends recent AB/game exposure toward a batting-slot expectation from load_lineup_adjustment. Clamped [0.8,1.2]. Called at 1204-1205. This is the ONLY per-batter opportunity/exposure knob today.
- **_park_factor_mult** (props.py:748-801 (called 1224-1226))
  park_mult factor for MLB batter_hits/pitcher_earned_runs: upcoming home park vs the player's recent park environment, strength-weighted.
- **_weather_factor_mult** (props.py:804-849 (called 1233-1234))
  weather_mult factor: temperature + wind nudge for MLB batter_hits/pitcher_earned_runs from the per-game weather forecast the caller passes.
- **prop_features.projection_multiplier (rest_mult)** (props.py:1245-1249)
  rest_mult factor from the §2.6 candidate-feature registry (rest/days-off). rest_strength defaults 0.0 -> 1.0 no-op in production.
- **per-past-game weight loop (opp-defense + venue)** (props.py:1088-1105)
  Builds the recency `weights` array: base _recency_weights(len,half_life) * _opponent_defense_multiplier (per prior opponent) * _venue_match_multiplier (per prior home/away). These reweight PRIOR games; they do NOT enter combined_mult, but they shape base_proj and the empirical over-rate.
- **player_context construction** (props.py:1180-1198)
  For MLB, computes expected_exposure = _weighted_mean(at_bats or plate_appearances, weights) (1187-1190) and packs {base_projection: base_proj, expected_exposure, batting_order}. This is the per-batter AB/game opportunity estimate and per-AB rate building block a joint model would aggregate.
- **_distributional_over_rate / _dist_p_over (method D)** (props.py:471-531 / 424-468)
  Binomial P(>=k hits): p_AB = clamp(level*quality_adj*rate_mult), n = round(expected_ab*exposure_mult), P = hits_at_least(k,n,p_AB). Crucially rate_mult (1284-1285) = output_def_mult*matchup_mult*park_mult*weather_mult (NOT lineup, NOT rest, NOT combined_mult); exposure_mult=lineup_mult. A GameContext folded only into combined_mult would BYPASS this path.
- **_negbin_over_rate (method E)** (props.py:534-552)
  NegBin survival with mean = avg_stat*mean_scale. Consumes avg_stat directly, so a GameContext folded into combined_mult flows here automatically. Ships nowhere in prod per memory.
- **build_matchup_features** (mlb_starters.py:867-1010+)
  The per-game feature producer. Signature (home_team, away_team, date, season, team_index=None). Returns {'home':{...},'away':{...},'starter_edge':float,'expected_runs':{...}}. Already computes a per-game run/edge signal but props only read the per-side starter/opp_offense sub-dicts.
- **analyze call site + matchup_features build** (app.py:2619-2620 and 2740-2748)
  build_matchup_features called ONCE per game in the plain per-event loop (2619); analyze_player_props_value called once per game passing matchup_features + weather (2740-2748). This whole loop is gated behind `if analyze_clicked` (app.py:2414); results stored in st.session_state['analysis_results'] (2781).

## DATA_FLOW
END-TO-END batter_hits projection: (1) history dict per (player,prop) supplies values[] (most-recent-first hits), at_bats[], opponents[], home_aways[], game_dates[], batting_order (props.py:1009-1017). (2) filter_player_gamelog drops low-min/layoff games -> eligible; values/at_bats/weights are rebuilt from eligible (1070-1075). (3) weights = _recency_weights(n,half_life) each multiplied per prior game by _opponent_defense_multiplier and _venue_match_multiplier (1088-1105). (4) base_proj = _weighted_mean(values,weights) (1122); optionally shrunk toward season mean (1123-1127) and blended toward xBA*AB/game via _xstats_blend (1159). (5) MULTIPLIER STACK, in this exact product order (1251-1252): combined_mult = output_def_mult (1.0 for MLB batters by default) * matchup_mult (_mlb_prop_matchup_mult opposing starter) * lineup_mult (_mlb_lineup_exposure_mult batting-slot exposure) * park_mult * weather_mult * rest_mult (1.0 default). (6) avg_stat = base_proj * combined_mult (1254). effective_line = line / combined_mult (1258). empirical_over = _weighted_rate(values, weights, v > effective_line) (1259) — i.e. the projection is scaled up, the comparison line scaled down by the inverse. (7) over_rate = empirical_over, then replaced by calibration: method D uses a binomial on rate_mult+exposure_mult separately (1276-1299), method E NegBin on avg_stat (1300-1318), else Platt/warmup on avg_stat vs line (1319-1334). (8) online Platt recal (1344-1359), then market-prior shrinkage toward de-vigged market (1576-1588). (9) edge/EV gate -> is_value (1591-1622). (10) ONE candidate dict per player appended (1669-1714) carrying avg_stat, over_rate, _values, _weights. KEY SHAPES: matchup_features = {'home': side, 'away': side, 'starter_edge': float, 'expected_runs': {...}} where side = {'starter': pitcher_quality, 'opp_offense_vs_hand': {'ops','k_pct'}, 'bullpen': {...}}; pitcher_quality (mlb_starters.py:733-766) = {name,throws,era,ip,avg_ip,bf,k_pct,bb_pct,xera,xwoba,xba,run_suppression,run_suppression_basis}. player_context = {base_projection, expected_exposure, batting_order}.

## GAMECONTEXT_RELEVANCE
WHAT EXISTS: (a) A per-game run/edge signal is ALREADY produced once per game by mlb_starters.build_matchup_features — starter_edge (mlb_starters.py:954) and result['expected_runs'] (1004+) — but props.py consumes ONLY matchup_features[opp_side]['starter'] and ['opp_offense_vs_hand'] (props.py:114,125-127). The game-level run/total signal is currently used only by team markets (moneyline/spreads/totals at app.py:2708-2712), never by batter props. (b) Per-batter opportunity is estimated: expected_exposure = weighted AB/game (props.py:1187-1190) and batter_rate = base_projection/expected_exposure (props.py:133) — the per-AB hit rate and AB count a bottom-up sum would need. (c) The matchup_mult already does a starter-vs-batter log5 blend with starter_share = clamp(avg_ip/9,0.10..0.80) (props.py:135,152-154). WHAT IS MISSING for a joint per-game GameContext: (1) NO shared run/pace/total distribution object — nothing holds a team run total or game total that batters sample from. (2) NO team-level aggregation of batter props ANYWHERE — confirmed: the loops iterate (prop_key -> player) independently (props.py:953,968) and append one flat candidate per player; sum-of-batter-hits is never formed, never compared to a team hits total, team run total, or game total. (3) NO reconciliation step (sum of batter hits <-> team hits <-> team runs <-> game total). (4) NO per-game pace/PA budget — expected_exposure is a per-batter recency mean, not derived from a projected team plate-appearance budget that would tie hitters together. (5) NO per-game caching of any such context (only build_matchup_features is built once/game). The only 'team' notions in props.py are player_team_name (venue/park lookups), team_defense (opponent points-allowed lookups), and matchup_features (opposing starter/lineup as INPUT) — all inputs, never an aggregated batter output.

## INTEGRATION_SEAMS
- PRODUCER: mlb_starters.build_matchup_features(home_team, away_team, date, season, team_index=None) -> dict (mlb_starters.py:867). A GameContext would be produced here (or a sibling builder) once per game — it already assembles starter_edge and expected_runs from the same StatsAPI/Savant inputs, so it is the natural home for a shared run/pace/total distribution.
- DRIVER: app.py:2619 builds matchup_features once per game; app.py:2740-2748 calls analyze_player_props_value(...). A GameContext must be produced near 2619 (once per game, cached per event id) and threaded in at 2740 — either as a new kwarg or attached onto matchup_features.
- ENTRY POINT: analyze_player_props_value(prop_data, player_histories, threshold_pct=5.0, sport_key=None, team_defense=None, espn_teams=None, safe_mode=False, safe_target=0.95, team_schedules=None, matchup_features=None, weather=None) (props.py:862-866). Add game_context here OR read it off matchup_features. Note prop_data already contains ALL players for the ONE game, so a team-grouping/aggregation pass can be added inside this function without new data.
- MEAN-COUNT SEAM: props.py:1251-1254 — combined_mult and avg_stat = base_proj*combined_mult. Folding a per-game context factor here auto-propagates to avg_stat, effective_line (1258), the empirical over-rate (1259), method E NegBin (1307-1309), and safe-mode wstd_adj (1391) / thresholds (1456).
- DISTRIBUTIONAL SEAM (must be threaded separately): props.py:1284-1285 rate_mult = output_def_mult*matchup_mult*park_mult*weather_mult and exposure_mult=lineup_mult passed to _distributional_over_rate(prop_key, line, values, at_bats, weights, rate_mult, exposure_mult, player_name, commence_iso, cfg, xstats_strength, teams=) (props.py:471-473). A GameContext folded only into combined_mult would BYPASS method D — it must also enter rate_mult and/or the p_AB level here.
- PER-BATTER RATE/EXPOSURE BUILDING BLOCKS: player_context {base_projection, expected_exposure, batting_order} (props.py:1192-1198) and batter_rate=base_projection/expected_exposure inside _mlb_prop_matchup_mult (props.py:133) — the per-AB rate and AB-count a moment-matched team sum would aggregate and reconcile.
- AGGREGATION GAP: there is NO existing function to hook; a new pre-pass (group player_histories by player_team_id via id_to_name at props.py:945-947 / player_team_name at 1082) or a two-phase loop would be required — phase 1 compute each batter's mean+variance, phase 2 reconcile to the GameContext total, phase 3 price. None exists today.

## RISKS
- LEAKAGE: the current path is strictly as-of — base_proj uses only eligible prior games dated before commence (filter at props.py:1043-1075), statcast_asof/get_rates is season-as-of, matchup_features uses season-to-date splits. A GameContext must preserve this: no same-day actuals, no post-commence data. Reconciliation across batters must use only pre-game projections.
- PER-RERUN COST is bounded because the entire analysis (including build_matchup_features and analyze_player_props_value) runs ONLY inside `if analyze_clicked` (app.py:2414) and results are cached in st.session_state['analysis_results'] (app.py:2781). Streamlit reruns (checkbox toggles, tab switches) re-render from session_state WITHOUT recomputation. So the 'no per-Streamlit-rerun Monte-Carlo' constraint is satisfied by keeping GameContext work in the analyze path; still it must be computed once per game (cache per event id like matchup_features), not once per (player,prop) — the per-player loop (props.py:968) has NO memoization and recomputes base_proj/combined_mult/avg_stat fresh for every player on each Analyze click.
- STDLIB-ONLY: no numpy/scipy. Analytic moment-matching must use the existing stdlib tools in stats.py — hits_at_least (binomial survival), negbin_at_least, _normal_inv_cdf, _weighted_mean/_std/_rate. No sampling.
- DOUBLE-COUNTING: matchup_mult already applies an opposing-starter log5 rate adjustment per batter (props.py:129-156) and park/weather already scale the run environment. A GameContext run/total factor that re-encodes starter/park/weather would double-count. The starter matchup, park, weather signals overlap with anything expected_runs-derived.
- TWO CALIBRATION PATHS diverge: mean-count methods (B/E, via avg_stat) vs distributional method D (via separate rate_mult+exposure_mult at props.py:1284-1285). A context factor must be threaded into BOTH or picks will be inconsistent depending on the per-bucket method.
- ORDERING: over_rate is transformed by residual calibration (1319-1334) -> online Platt (1344-1359) -> market-prior shrinkage toward market (1576-1588). A reconciled projection changes over_rate before Platt; Platt params were fit against raw_over_rate (logged at 1655) so a structural change to how over_rate is produced could invalidate existing fits. raw_over_rate is snapshotted at 1340 and logged for future refits — a reconciliation layer must decide whether it logs pre- or post-reconciliation to avoid contaminating Platt.
- COUPLING/OUTPUT CONTRACT: each candidate carries _values/_weights (props.py:1562-1563,1712-1713) consumed by parlay correlation logic; a joint model that prices batters together must still emit these per-leg or update the parlay consumer. Safe-mode branch (1370-1565) has its own threshold search that re-derives probabilities via combined_mult and _probability_at_threshold — any reconciliation must be mirrored there or safe-mode picks will silently diverge from standard picks.
