## DATA_FLOW
PIPELINE: harvest_real_line_book_lines(sport_key,target_props,store_label) pulls real DK/consensus book lines from the Azure warehouse + prediction log; join_book_lines_to_actuals(...) attaches graded outcomes => `enriched`, a list of `obs` dicts.

OBS SHAPE (consumed by project_and_empirical): obs = {prior_games: [ {H, AB, IP, MIN, is_home, opponent, game_date, <stat_label>}, ... ], stat_label, line (raw book line, float), test_game: {is_home}, actual, game_date, player, prop_key, over_price, under_price}.

PARAMS SHAPE (dict, assembled per prop): TODAY the keys are half_life, venue_strength (0.0 default), opp_defense_strength (0.0 default), use_minutes (bool), rest_strength (float, the feature runtime_knob), and optionally features={name:strength} (diagnostic injection) plus center ('mean'|'median') and home_ab_delta (project_distributional only). params flows cfg -> build_real_line_obs(enriched, params, ...) -> project_and_empirical(obs, params, ...). Inside project_and_empirical, prop_features.strengths_from_params(params) collapses rest_strength + features into {name:strength}; prop_features.projection_multiplier turns that into a single scalar feat_mult keyed on (prop_key, this obs's own prior_game_dates, this obs's game_date).

PROJECTION: project_and_empirical returns two floats per obs: projected (recency x venue x opp_defense center estimate, optionally xBA-blended, then * feat_mult) and empirical_over (weighted rate of prior_values above line_eff=line/feat_mult). build_real_line_obs packs these into row = {player, projected, line, actual, empirical_over, game_date, over_price, under_price}.

METHOD SELECTION: select_method_at_real_lines(rows) => on usable rows (actual!=line, >=20) it scores A/B/C(/D/E) Brier on a single 50/50 chronological holdout (_score_abc_real) plus two expanding folds (_real_line_folds), applies the confirmation gate, and returns {method, fit_brier, baseline_brier, cv_brier, confirmed, residual_mu, residual_sigma, residual_ecdf, n_obs, single_split, roi_tiebreak}.

DATA OUT: refit_sport_real_lines merges method + residual_mu/sigma/ecdf into calibration/<sport>.json. At runtime props.analyze_player_props_value reads that cfg, recomputes empirical_over at the real line, and (for A/B/C/E) applies residual_mu/sigma/ecdf to produce the shipped P(over); rest_strength (and any future feature knob) re-derives feat_mult live via the SAME prop_features.projection_multiplier.

## GAMECONTEXT_RELEVANCE
WHAT EXISTS TODAY that is game/team/pace-adjacent: (1) matchup_mult via _mlb_prop_matchup_mult (props.py:93-162) reads a per-game `matchup_features` dict shaped {home:{opp_offense_vs_hand:{ops,k_pct}, starter:{xba,k_pct,avg_ip,bf}}, away:{...}} and produces a bounded per-PLAYER projection multiplier (log5 batter-vs-starter for batter_hits; opp-lineup-vs-hand for pitcher props). It bounds to [0.7,1.4]. (2) opp_defense_strength weight-side term (opp_defense_mult) reweights prior games by opponent run-prevention. (3) park_mult and weather_mult are per-game environment multipliers. (4) The distributional method D (project_distributional / props._dist_p_over) already models a batter's hits as Binomial(n=expected_AB, p=per-AB rate) with rate_mult and exposure_mult hooks — the closest thing to a moment-matched count model, and the natural place a shared team run/total would reconcile.

WHAT IS MISSING for a per-game joint GameContext: there is NO shared per-game object. Every multiplier is computed independently per player from that player's OWN prior games; matchup_features carries team/starter aggregates but is never turned into a single run/total distribution, and nothing sums batter hits -> team hits -> team runs -> game total. Critically for the gate: project_and_empirical (the offline scorer) applies ONLY recency/venue/opp_defense/xBA/feat_mult — it does NOT apply matchup_mult, park, weather, or lineup. So none of the existing per-game signals are currently visible to the confirmation gate; only opp_defense_strength (a weight-side knob) and the prop_features feat_mult are. A GameContext-derived batter adjustment therefore has exactly one offline-gate-visible seam today: the prop_features feat_mult (projected*=feat_mult; line_eff=line/feat_mult). There is no per-game cache, no shared-distribution object, and no cross-batter reconciliation anywhere in the calibration or projection code.

## RISKS
- LEAKAGE: the entire gate assumes leakage-safe as-of construction. project_and_empirical feeds only prior_games (strictly before obs game_date) and obs.game_date to the feature; prop_features.rest_multiplier re-filters to dates < graded_date (L82-83). A GameContext value MUST be computed as-of (only info available before commence) or the confirmation folds become invalid — the folds cannot detect leakage, they assume it away.
- GATE-EXPRESSIBILITY: the ONLY offline-gate-visible seam is a per-observation scalar feat_mult applied as projected*=feat_mult; line_eff=line/feat_mult. A joint GameContext output must be reducible to such a scalar PER (batter obs), or it cannot be Brier-scored by select_method_at_real_lines and cannot 'ship'. A distribution-level reconciliation (sum of batter hits <-> team total) that changes the SHAPE (variance) but not the mean-at-line cannot ride the feat_mult seam — it would need a new method (like D/E) wired into _score_abc_real (book_line_calibration.py:865-912) and the candidate_methods list (L1068-1072), plus its own p_dist per row.
- GATE STRENGTH: MIN_CALIB_BRIER_GAIN=0.002 single-split + BOTH-fold confirmation (_confirms) + (sweep) _variant_confirms is a HIGH bar — per MEMORY, rest ships nowhere, NegBin E ships nowhere, xBA/CSW don't ship. A GameContext adjustment competes against the same bar and against an empirical baseline A that recomputes over-rate at the real line for free. It needs a real, out-of-sample, two-fold Brier gain to survive.
- METHOD-D BLIND SPOT: project_distributional (method D) does NOT read feat_strengths (book_line_calibration.py:615-701) — it applies rate_mult=1.0, exposure_mult=1.0 offline. A feat_mult would move A/B/C/E but leave D unchanged, so for batter_hits (where D is the line-conditional candidate) a GameContext multiplier would be inconsistent across methods unless project_distributional is also taught to consume it.
- PER-RERUN COST / NO MC: design constraint is analytic moment-matching cached per game, but there is NO per-game cache today — obs are per-player. A GameContext object would be a new construct; building it inside project_and_empirical per-obs (called once per row, thousands of rows in a refit) would be O(rows) unless memoized per game_id. The stdlib-only, no-numpy constraint means any moment-matching must be hand-rolled (see stats.fit_negbin_dispersion, _norm_cdf, _empirical_cdf as the existing hand-rolled precedents).
- OBS HAS NO SHARED STATE: obs dicts carry only one player's data plus opponent name; there is no game_id, no roster, no opposing-lineup handle, and no team-total field. Producing a joint GameContext requires augmenting enriched upstream in join_book_lines_to_actuals (or a parallel per-game index passed into build_real_line_obs) — a new plumbing seam, not just a new registry entry.
- COUPLING: prop_features is the ONE source shared by offline gate, synthetic sweep, and runtime (per its module docstring); a GameContext feature added there must be a pure bounded multiplier or it breaks the invariant that strength 0 == production byte-for-byte (the diagnostic self-check at diagnose_features and the runtime default rest_strength=0.0). Any richer joint behavior likely belongs in a NEW seam rather than overloading projection_multiplier's (prop_key, strength, dates) contract.
- SWEEP GRID GROWTH: adding a feature axis to _parse_variant_name / the sweep grid multiplies the (variant x method) candidate count (already ~250 per P1.4 note); more candidates on one split worsen winner's-curse, which is exactly what the two-fold gate exists to counter — but it also means a real signal can be masked if the grid is too wide relative to obs count (batter_hits real-line obs ~938 per MEMORY).
